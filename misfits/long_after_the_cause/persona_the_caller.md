# Persona: The Caller

## Taxonomy

[Caller](position_caller.md). The client that reissues a request when it times out, doing exactly what every guide prescribes, and by doing so feeding the loop that made it time out.

## Owner

- Project: khai-misfits

## Projection

Well built and well behaved, a client that handles failure properly instead of dropping the user's request on the floor.
Retries on timeout, as the documentation says to and as the default configuration already does, the mark of a client written by someone who read the guidance.
No excess on show: one request that failed, tried again, which is the smallest and most obviously correct thing a client can do.

## Action

Runs [Try It Again](plan_try_it_again.md): through [Retrying](process_retrying.md) at [the Fleet](place_the_fleet.md), reissues what timed out, and reissues again if the second attempt times out too.
Cannot see the other callers doing the identical correct thing at the identical moment, since it holds no model of the fleet and was never given one.
Does what correctness requires: a request that failed and might succeed on another attempt is retried, and a client that gave up on the first timeout would be the defective one.

## Shadow

Not reckless: the retry is prescribed practice, shipped on by default, and the right call for any single request considered alone, which is the only way this persona can consider one.
Because a timeout is generated by load and its retry is added to load, its correct response to failure is the thing that manufactures the next failure, so the more faithfully it follows the guidance the harder the system is held down.
It is the well-written client, and the engine of the loop.

## Tell

Reports rising error rates and rising retry counts together, and reads the second as its proper answer to the first rather than as its cause.
Cannot tell a system that is briefly slow from one it is helping to pin, since both look identical from a single caller's vantage: a request that timed out and deserves another try.
